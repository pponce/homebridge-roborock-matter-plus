Suggested title: **Wait for MQTT reply readiness without blocking a working LAN route**

## Replacement PR description

Cloud requests can arrive before the MQTT reply subscription is ready. This change waits up to ten seconds before sending, with no pending RPC and no robot-response budget consumed during the wait. Readiness expiry is classified as not sent, so it does not increment unanswered-request evidence or the method breaker.

The gate is event-driven and cancelled on disconnect. preferCloud falls back to a working LAN connection when MQTT is disconnected or not ready. Requests that require MQTT retain the bounded wait. v3.39.0 client retirement, publish failures, shutdown handling and disabled QoS-zero queueing are preserved.

Based directly on v3.39.0. Merge before #31, which now uses this gate. The TCP-probe fix is separate.

Live validation remains pending before this leaves draft: a brief reconnect and an outage over ten seconds, each tested through a Matter command and a HAP switch, recording Apple Home behavior and timestamps. Automated results do not establish the visible Home UI behavior.

## Review reply to post

Thanks Mathias. Rebased onto v3.39.0, with the probe-test change removed.

A preferCloud request now uses a working LAN route when MQTT is disconnected or its reply subscription is not ready. The regression tests cover both cases. Requests that actually require the cloud still get the bounded readiness wait.

The readiness gate is event-driven, with one deadline timer per waiter. It reads the connection/subscription flags directly and is notified by readiness and disconnect events; there is no 25 ms snapshot polling. Waiting creates no pending RPC, the response budget starts after publish, and expiry is still classified as not sent.

The v3.39.0 previous-client retirement, mqtt.js listener guards, QoS-zero behavior, publish-callback errors and shutdown behavior are preserved. #31 has been updated to use this gate and remains dependent on this PR.
