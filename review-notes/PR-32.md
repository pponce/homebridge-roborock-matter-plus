## Replacement PR description

A schedule write can apply even when its acknowledgement is lost. This change reads back the written source before deciding whether another assignment is needed, and never treats retained data from a failed source as fresh confirmation.

Ambiguous primary and fallback writes are verified. A matching fresh read confirms the requested state; one bounded fallback is allowed only when a trusted read finds the existing schedule in the opposite state. Missing schedules, explicit refusals, failed verification and shutdown do not authorize retries. Cloud-scene fallback uses fresh scene data to preserve app edits. Routine execution is never retried.

Repeated matching pending requests share one operation. An intervening opposite intent may cause on → off → on to send on twice. Summary logs retain primaryConfirmed and fallbackSent.

An explicit throttle from either read source pauses this account's schedule traffic for 65 minutes, including partial-success periodic refreshes. Failed switch writes preserve v3.39.0's HapStatusError behavior; optimistic display is separate in #38.

Based directly on v3.39.0, independent of #30/#31. Tests retain real queue timeouts and HTTP applied-then-disconnected failures. The TCP-probe fix is separate. Refs #27.
