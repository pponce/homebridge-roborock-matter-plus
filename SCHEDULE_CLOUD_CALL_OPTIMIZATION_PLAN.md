# Schedule Cloud-Call Optimization Plan

## Purpose

Reduce Roborock cloud traffic generated by HomeKit schedule reads and multi-switch schedule writes
without expanding Pedro's contribution into unrelated polling, transport, map, or HomeData code.

This plan corresponds specifically to findings 2 and 3 of the cloud-call review:

1. duplicated and overly frequent schedule refreshes; and
2. schedule-write bursts when scenes or automations change many switches together.

## Scope boundary

### In scope

- Schedule coordinator cache ownership, refresh cadence, failure recovery, and stale-state behavior.
- Removal of redundant server-schedule reads while the schedule coordinator owns that data.
- Investigation of whether `get_timer` is a separate legacy facility with real consumers.
- Per-vacuum ordering of schedule writes.
- Coordination of schedule traffic across every configured vacuum on one Roborock account.
- Coalescing, spacing, optimistic state, consolidated verification, and throttle-aware batch
  cancellation for schedule writes.
- Configuration, tests, logs, and live validation required by those schedule changes.

### Out of scope

- HomeData refresh policy or a plugin-wide account request governor.
- General robot status, settings, consumables, or room-mapping polling.
- Live-room/map cadence, B01 active-map caching, or classic live-map failure backoff.
- General LAN-to-cloud fallback policy.
- A redesign of the plugin's common cloud or MQTT transport.
- Pedro's Script2 pause/restore implementation and its polling cadence.

The out-of-scope findings should be summarized for Mathias with their evidence, estimated request
volumes, and suggested approaches. Mathias can decide whether he wants to implement them. They must
not enter Pedro's schedule implementation without a later explicit scope decision.

### External orchestration boundary

Pedro is developing the Script2 pause/restore script in parallel and will adapt that script after
the plugin's schedule read and write contracts are finalized. The plugin must provide a safe,
generic schedule surface for HomeKit clients, scenes, and automations; it must not encode behavior
specifically for Script2 or depend on Script2 for batching, retry, or correctness.

During implementation:

- Do not use Script2's current one-minute activity as a requirement for plugin refresh cadence.
- Do not modify or test Pedro's Script2 scripts as part of this plan.
- Test frequent independent HomeKit readers generically so Script2 and other clients receive the
  same cache protection.
- Keep batching and throttling inside the plugin, because an arbitrary scene or HomeKit client can
  still change many switches without Script2.
- Document the finalized observable timing and failure behavior so Pedro can update his script after
  the plugin behavior is stable.

## Finding 2: schedule reads and recovery

### Starting behavior to verify

The review observed the following behavior before implementation:

- A 60-second successful cache TTL.
- A 30-second failure backoff.
- One cached schedule list per vacuum coordinator.
- A shared in-flight promise, so simultaneous switch reads normally join one refresh.
- HomeKit getters that return their current value and start refresh asynchronously.
- Schedule requests that explicitly set `preferCloud: true`.
- A generic periodic poll that separately invokes both `get_server_timer` and `get_timer`.

Recheck every observation against the latest merged `main` before changing code. Upstream may have
altered schedule ownership or timing since the review.

The current trace has already exposed an important qualification: the generic poll names
`get_server_timer` and `get_timer`, but the lower vacuum implementation appears to send those
requests only while its debug flag is enabled. Phase 1 must prove the effective Homebridge runtime
value of that flag and check every alternate caller. Do not present the generic-poll component as
normal steady-state traffic until that trace proves it.

### Request-volume context

Let `N` be the number of configured vacuums on an account. The review identified this theoretical
ceiling before schedule writes:

- Up to `60 × N` reads per hour from HomeKit-facing coordinators if HomeKit repeatedly asks after the
  one-minute TTL.
- If the lower debug/request gate is open, another `20 × N` `get_server_timer` reads per hour from
  the three-minute generic polls.
- With that gate open, approximately `80 × N` schedule reads per hour at the theoretical ceiling;
  with it closed, the coordinator-only ceiling is `60 × N`.

For Pedro's current two-vacuum installation, `N = 2`, so the example ceiling is 160 reads per hour.
That is a field-validation example, not an architectural limit or an assumption to encode in code.

This is not a measured steady-state rate. The HomeKit portion depends on actual getter frequency.

After the proposed five-minute coordinator TTL, the coordinator-only ceiling becomes `12 × N`.
Suppressing the generic reader matters only in the modes where the trace proves it actually sends a
request.

### Intended ownership model

Make the schedule coordinator the sole owner of server-schedule reads while schedule switches are
enabled.

Initial policy:

- Successful cache TTL: five minutes.
- Return stale cached state immediately while a refresh is due or recovering.
- Approximate failure sequence: 1, 2, 5, 15, and 60 minutes.
- Add jitter so any number of vacuums do not retry in lockstep.
- Perform an explicit refresh after a completed user-write batch.
- Suppress generic `get_server_timer` polling while the schedule coordinator owns server schedules.
- Preserve the existing shared in-flight behavior.
- Continue distinguishing an authoritative empty list from a failed refresh; failure must not remove
  schedule services.

### `get_timer` decision

Trace all producers, consumers, model gates, and tests for `get_timer` before changing it.

- Retain it if it is a genuinely distinct legacy timer facility used by another feature or device
  family.
- Remove or suppress it only if evidence proves the schedule coordinator owns the same data and no
  independent consumer remains.
- Do not remove it merely because its name resembles `get_server_timer`.

## Finding 3: schedule-write bursts

### Starting behavior to verify

The review observed independent bookkeeping per schedule switch. One requested switch change can:

1. Send `upd_server_timer`.
2. Wait approximately three seconds and verify with a schedule read.
3. Send fallback `upd_timer` if primary verification fails.
4. Verify again.

Let `S` be the total number of schedule switches changed by one scene or automation across all
configured vacuums. Without coordination, one scene can initiate `S` workflows concurrently:

- Normal confirmed path: as many as `S` writes plus `S` verification reads, or `2 × S` operations.
- Full fallback path: as many as `S` primary writes, `S` reads, `S` fallback writes, and `S` more
  reads, or `4 × S` operations.

Pedro currently has 15 switches split across two vacuums, so his field example is 30 operations on
the normal path or 60 on the full fallback path. The queue and coordinator must not assume either
the number of vacuums or the number of switches.

Lower-layer retries may increase the effective wire count. Verify current behavior after the
upstream merge rather than treating these figures as permanent implementation facts.

### Intended architecture

#### Account-aware schedule coordinator

- Coordinate schedule traffic across every configured vacuum sharing an account.
- Limit concurrent schedule-cloud operations across the account.
- Own schedule throttle/cooldown state shared by all vacuums on that account.
- Stop or pause pending schedule work after a definite throttle response.
- Do not turn this schedule-specific component into the out-of-scope general HomeData governor.

#### Per-vacuum write queue

- Preserve command order for one robot.
- Prevent independent schedule switches from running overlapping write/verify workflows.
- Allow every per-vacuum queue to be arbitrated by the account-aware schedule coordinator.

#### Coalescing

- Start with an approximately 500 ms coalescing window.
- When one schedule is toggled repeatedly within the window, retain only its final requested value.
- Preserve the final requested state for every distinct schedule in the batch.
- Make the window configurable only with safe validation and a conservative minimum.

#### State and verification

- Optimistically update the coordinator cache so HomeKit reflects the requested final state without
  waiting for every network round trip.
- Space writes conservatively; make spacing configurable with a safe default and minimum.
- Verify once after the batch rather than once after every switch.
- Compare the authoritative result with every schedule modified by the batch.
- Retain the reviewed `upd_timer` fallback behavior, but invoke it in an ordered, bounded way rather
  than through `S` independent workflows.
- On a definite throttle response, do not continue issuing requests known to be doomed.

## Compatibility with deferred HomeData work

The current library reuses one 180-second `updateInterval` for the account HomeData timer and every
vacuum's generic poll. Schedule coordinator reads and write verification use separate timing state.
This plan must preserve that semantic separation so Mathias can later split or replace the shared
HomeData/poll interval without rewriting schedule behavior.

Design rules:

- Do not derive schedule TTL, failure backoff, batch window, write spacing, or cooldown from
  `updateInterval`.
- Do not mark schedules fresh because HomeData succeeded, and do not invalidate schedules because
  HomeData failed.
- Keep the account-aware coordinator limited to schedule traffic. It may coordinate every vacuum's
  schedule queue, but it must not become a second general cloud governor.
- Keep schedule requests on the existing common API/transport path so a future global governor can
  wrap them.
- Allow a future global governor to supply an account-level "not before" time. A schedule request is
  eligible only after both that time and its schedule-specific backoff have expired.
- Report schedule request metrics separately from HomeData, maps, status, and LAN-to-cloud fallback.
- State clearly that schedule optimization cannot guarantee freedom from account throttling while
  other cloud consumers remain unchanged.

The deferred HomeData work and this schedule work are complementary: a future global governor asks
whether the account may make a cloud request, while the schedule coordinator asks which schedule
request is necessary and should run next.

## Implementation sequence

### Phase 1: verify current merged behavior

- Trace schedule refresh ownership from HomeKit getters through the coordinator and Roborock API.
- Trace generic `get_server_timer` and `get_timer` polling and every consumer.
- Prove whether the lower debug gate sends either generic timer request in normal Homebridge
  operation, debug operation, or both; correct the request-volume model from that evidence.
- Trace the complete primary-write, verification, fallback-write, and second-verification path.
- Identify where account identity and per-vacuum identity are available for coordination.
- Identify the narrow integration point where a future common account governor could delay schedule
  work without owning schedule queue state.
- Update this plan when current code differs from the original review.

#### Phase 1 audit result

- The platform passes its explicit `debugMode` setting into the Roborock library's `debug` option.
- The generic three-minute poll visits the `get_server_timer` and `get_timer` branches, but both
  lower branches call `sendParameterRequest` only when that debug option is enabled.
- Therefore the extra `20 × N` estimate is a debug-mode diagnostic ceiling, not normal-mode
  schedule traffic.
- `get_timer` populates the distinct `lastTimer` diagnostic consumed by the settings UI. Retain it;
  it is not coordinator-owned server-schedule state merely because its method name is similar.
- `get_server_timer` also populates a diagnostic snapshot in debug mode. Do not remove that explicit
  diagnostic request in the first read-policy patch; the five-minute coordinator cache and
  progressive failure backoff address normal schedule traffic without degrading diagnostics.
- Source-contract coverage pins these gates so a future refactor cannot silently turn the diagnostic
  branches into normal periodic requests.

### Phase 2: schedule-read ownership and recovery

- Make cache and backoff constants explicit and testable.
- Implement the five-minute successful TTL and jittered progressive failure delays.
- Preserve stale immediate reads and the shared in-flight refresh.
- Suppress redundant `get_server_timer` polling while schedule switches own that data.
- Decide `get_timer` from traced evidence.
- Add focused request-count, stale-state, recovery, and multi-vacuum jitter tests.

### Phase 3: write coordination and batching

- Add the account-aware schedule coordinator.
- Add one ordered queue per vacuum.
- Add the coalescing window and final-value conflict handling.
- Add safe write spacing and optimistic cache updates.
- Consolidate verification at batch completion.
- Integrate bounded fallback and throttle cancellation.
- Add tests for one and multiple vacuums, unequal schedule counts, Pedro's 8-and-7 field scenario,
  repeated toggles of one schedule, simultaneous vacuum queues, fallback, partial failure, shutdown,
  restart, and definite throttling.

#### Phase 3 checkpoint: per-vacuum serialization

- Each vacuum coordinator now owns an ordered schedule-write queue.
- Different schedule switches on one vacuum can no longer overlap their write/verify workflows.
- A rejected operation does not poison later queued work.
- Shutdown cancels work that is still pending while allowing an already running operation to settle;
  a later initialization can enqueue new work normally.
- Separate vacuum coordinators retain separate queues, so one slow vacuum does not block another.
- Coalescing, spacing, consolidated verification, account arbitration, and throttle cancellation remain
  later checkpoints and are not implied by serialization alone.

#### Phase 3 checkpoint: coalescing

- Each vacuum collects schedule changes for 500 ms before dispatch.
- Repeated changes to one schedule within that window resolve the superseded request locally and send
  only the final requested value.
- Distinct schedules retain their first-seen order while carrying their final requested values.
- The collected operations still pass through the per-vacuum serial queue after the window closes.
- Shutdown clears the timer, resolves undispatched requests without sending them, and cancels work
  already waiting behind the current queue operation.
- Existing single-switch behavioral coverage now advances through both the batch window and the
  verification delay.
- End-to-end HAP coverage proves that rapid on/off/on changes on one real schedule service emit only
  the final `upd_server_timer` command and one verification read.

#### Phase 3 checkpoint: consolidated verification

- A collected per-vacuum batch sends its final primary writes in order, waits once, and performs one
  authoritative `get_server_timer` verification read for the entire batch.
- Schedules already confirmed by that snapshot complete without an individual verification read.
- Only schedules not confirmed by the primary snapshot enter the bounded `upd_timer` fallback phase.
- Successfully sent fallbacks share one final authoritative verification read; each caller still
  receives success or failure for its own schedule.
- A primary or fallback send failure is isolated to that schedule and does not poison other changes
  in the same batch.
- End-to-end HAP coverage proves that two distinct schedules changed together produce two ordered
  writes and one verification read, instead of two write/verify workflows.
- Safe inter-write spacing, definite-throttle cancellation, and account-wide arbitration remain
  later checkpoints and are not implied by consolidated per-vacuum verification.

#### Phase 3 checkpoint: conservative write spacing

- Distinct primary writes within one vacuum batch are separated by 500 ms rather than being emitted
  back-to-back.
- Multiple bounded fallback writes use the same spacing policy.
- A single-schedule change incurs no additional spacing delay; the delay exists only between writes.
- The spacing timers use the shared timer utility and do not keep the Homebridge process alive.
- Definite-throttle cancellation and account-wide arbitration remain later checkpoints. Per-vacuum
  spacing alone cannot coordinate simultaneous batches belonging to different vacuums.

#### Phase 3 checkpoint: definite-throttle cancellation

- Structured HTTP status/status-code `429` errors and explicit rate-limit/throttle messages are
  recognized as definite throttling; timeouts, offline errors, and maintenance responses are not.
- A definite throttle on a primary write stops the rest of that vacuum batch immediately and skips
  its verification read and all fallbacks.
- A definite throttle during fallback stops the remaining fallback writes and skips the final
  verification read.
- Pending batches for that vacuum are canceled, and later schedule reads or writes are held behind a
  conservative 65-minute schedule cooldown rather than probing the capped service repeatedly.
- Every affected HomeKit write receives a failure and returns to its previous state instead of being
  reported as confirmed.
- Definite-throttle recognition originates in the vacuum performing the request; the following
  checkpoint shares the resulting cooldown and arbitration across the account.

#### Phase 3 checkpoint: account-wide schedule arbitration

- The platform now owns one schedule account coordinator and supplies the same instance to every
  configured vacuum's schedule coordinator.
- Complete per-vacuum batches are serialized through that shared coordinator, so schedule traffic
  from different vacuums cannot overlap even though each vacuum retains its own local queue and
  coalescing window.
- A definite throttle reported by one vacuum establishes the shared 65-minute schedule cooldown.
- Batches already waiting for other vacuums are rejected locally when they reach the account
  coordinator; they do not send a probe merely to rediscover the same account throttle.
- Per-vacuum ordering, final-value coalescing, consolidated verification, and fallback isolation are
  preserved beneath the account-wide layer.
- This coordinator remains schedule-specific. It does not govern HomeData, maps, status polling, or
  unrelated cloud commands and can later sit beneath a general governor owned by Mathias's code.

#### Phase 4 checkpoint: schedule traffic observability

- Startup logs the effective five-minute cache, 500 ms batch window, 500 ms write spacing, and
  65-minute definite-throttle cooldown once when schedule switches are enabled.
- The account coordinator keeps separate cumulative counters for schedule reads, primary writes,
  fallback writes, coalesced changes, cache-avoided reads, backoff-avoided reads, and operations
  avoided during throttle cooldown.
- Request counters are incremented when an actual cloud attempt begins, including failed attempts;
  locally avoided work is never mislabeled as a sent request.
- A debug summary after each completed write batch exposes the account totals without logging
  credentials, complete schedule payloads, or device secrets.
- These metrics cover schedule traffic only and therefore cannot be mistaken for HomeData, map,
  status, or total Roborock cloud usage.

#### Phase 4 checkpoint: safe schedule policy configuration

- The Homebridge schema and custom settings UI expose schedule refresh minutes, batch-window
  milliseconds, write-spacing milliseconds, and definite-throttle cooldown minutes with units in
  every setting name and label.
- Omitted settings preserve the reviewed defaults: 5 minutes, 500 ms, 500 ms, and 65 minutes.
- Runtime validation accepts finite numbers and numeric strings only within conservative bounds;
  empty strings, zero, negative values, `NaN`, infinity, nonnumeric strings, and extreme values fall
  back to the safe default.
- Minimums are 1 minute for successful schedule cache, 100 ms for batching, 250 ms for write
  spacing, and 60 minutes for a definite-throttle cooldown.
- Maximums prevent accidental effectively-permanent disabling: 24 hours for cache/cooldown, 5
  seconds for batching, and 10 seconds for write spacing.
- The effective validated policy continues to be logged once at startup.

#### Phase 5 checkpoint: deterministic integration gate

- End-to-end HAP tests now cover the normal consolidated path, final-value coalescing, exact
  inter-write spacing, an explicit throttle, a mixed batch with one primary-write failure, and a
  mixed verification result that sends one bounded fallback followed by one final verification.
- The partial-failure case proves one rejected schedule returns to its previous Home state without
  poisoning another successfully confirmed schedule in the same batch.
- The fallback case proves an already-confirmed schedule is not written again and only the
  unconfirmed schedule reaches `upd_timer`.
- All schedule-focused tests, TypeScript checks, formatting, and whitespace validation must pass
  before branch integration or live installation.
- Live cloud success remains deferred while Pedro's account is capped; deterministic coverage is the
  release gate until a single controlled field test is safe.

- Count schedule reads, primary writes, fallback writes, verification reads, coalesced changes, and

- Keep logs free of credentials, device secrets, and complete schedule payloads.

## Acceptance criteria

- The schedule coordinator is the only server-schedule reader while it owns schedule switches.
- A cloud failure never removes cached schedule services or loses their Home names/identity.
- Any number of configured vacuums avoid retrying schedule reads in lockstep.
- A scene changing `S` switches produces ordered, bounded traffic rather than `S` concurrent
  verification flows.
- Repeated changes to one switch within the coalescing window send only its final requested state.
- One authoritative batch verification reconciles every changed schedule.
- A definite throttle response stops remaining doomed schedule operations.
- Distinct legacy `get_timer` behavior remains intact unless traced evidence supports its removal.
- No HomeData, live-map, general polling, or common-transport redesign enters the patch.
- The live branch retains Pedro's Markdown and generated `dist/` and installs successfully through
  the documented `hb-service` procedure.

## Current live-test constraint

Pedro's Roborock account is currently encountering the cloud caps this work is intended to reduce.
Live cloud calls may therefore fail even on the known-good baseline and must not be used alone to
judge whether a candidate implementation is correct.

Until the account has clearly recovered:

- Prefer passive log collection and deterministic tests over repeated live requests.
- Do not repeatedly toggle a schedule, run the full pause/restore scene, restart the plugin, or force
  refreshes merely to obtain a successful response.
- Treat an explicit throttle, timeout, or cloud refusal as field evidence and stop the test rather
  than retrying it.
- Record the time, operation class, affected vacuum, whether a request was actually sent, and the
  first failure response without recording credentials or complete payloads.
- Distinguish a baseline cloud-cap failure from a regression: correctness must be established with
  unit/integration tests and later confirmed live after recovery.
- Use the eventual live test first to verify that backoff and batch cancellation avoid extra calls;
  only then test successful state reconciliation.

The implementation must remain useful under this condition: stale schedule services stay present,
queued work stops on a definite throttle, and failures do not cause a retry storm.

## Post-merge follow-up: ten-minute successful-read TTL

- The successful schedule snapshot TTL is now 10 minutes rather than the 5-minute value shipped in
  3.22.0. Under continuous HomeKit reads, this lowers the coordinator-only theoretical ceiling from
  `12 × N` schedule reads per hour to `6 × N`, where `N` is the number of configured vacuums.
- This remains a ceiling rather than an expected steady-state rate: a vacuum is read only after its
  successful snapshot expires and another HomeKit read asks for schedule state.
- HomeKit schedule writes do not wait for the TTL. They still perform their own consolidated,
  authoritative verification after the write batch.
- The longer stale-state bound therefore applies only to schedule changes made outside this bridge,
  such as a change made directly in the Roborock app.
- Startup discovery, write verification, recovery after failures, and explicitly enabled diagnostic
  probes are separate request sources and are not included in the `6 × N` cache-driven ceiling.
